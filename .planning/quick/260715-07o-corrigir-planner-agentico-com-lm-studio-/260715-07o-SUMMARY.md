# Quick 260715-07o: Corrigir planner agêntico com LM Studio Summary

Fix provider-aware no `generatePlan` — quando `LLM_PROVIDER=lmstudio`, `withStructuredOutput` passa a usar `{ method: 'jsonSchema' }` em vez do `functionCalling` default, que enviava `tool_choice` em formato objeto (rejeitado pelo LM Studio com HTTP 400). OpenAI/Anthropic/Gemini/OpenRouter continuam com a chamada original, sem segundo argumento.

## O que foi feito

### Task 1 — Threading provider-aware do método jsonSchema

- `apps/backend-ts/src/agent/planner.ts`:
  - Adicionada constante de módulo `JSON_SCHEMA_STRUCTURED_OUTPUT_PROVIDERS = new Set(['lmstudio'])`.
  - `GeneratePlanOptions` ganhou campo opcional `provider?: string`.
  - `generatePlan()` agora escolhe condicionalmente: se `options.provider` está no set, chama `llm.withStructuredOutput(planSchema, { method: 'jsonSchema' })`; caso contrário, mantém a chamada original `llm.withStructuredOutput(planSchema)` sem segundo argumento.
- `apps/backend-ts/src/agent/graph.ts`:
  - `BuildTaskGraphArgs` ganhou campo opcional `provider?: string`.
  - O node `'planner'` repassa `provider: args.provider` para `generatePlan`.
- `apps/backend-ts/src/session/chat-session.ts`:
  - `getOrCreateAgenticGraph()` passa `provider: this._activeProvider` (campo já existente desde a Fase 63) para `buildTaskGraph`.

### Task 2 — Testes do branch provider-aware

- `apps/backend-ts/src/agent/__tests__/fixtures/mockChatModel.ts`:
  - `MockOptions` ganhou campo opcional `capturedStructuredOutputConfigs?: unknown[]`.
  - `withStructuredOutput` do mock agora aceita um segundo argumento (`structuredConfig`) e o empurra para `capturedStructuredOutputConfigs` quando fornecido — mudança puramente aditiva.
- `apps/backend-ts/src/agent/__tests__/planner.test.ts`:
  - Novo `describe('generatePlan — provider-aware structured output method (Quick 260715-07o)')` com 3 casos: `provider: 'lmstudio'` → `{ method: 'jsonSchema' }`; `provider: 'openai'` → `undefined`; provider omitido → `undefined`.
- `apps/backend-ts/src/agent/__tests__/graph.test.ts`:
  - Novo `describe('provider-aware structured output threading (Quick 260715-07o)')` com 1 teste provando o threading ponta-a-ponta `buildTaskGraph({ provider: 'lmstudio' })` → node `'planner'` → `generatePlan` → `withStructuredOutput`.

`executor.ts` e os call sites de `createReactAgent` em `chat-session.ts` não foram alterados — confirmado via grep que nenhum define `tool_choice` (a ausência já garante `'auto'` default, aceito pelo LM Studio).

## Decisões de design

- **Set restrito a `'lmstudio'`**: `JSON_SCHEMA_STRUCTURED_OUTPUT_PROVIDERS` não inclui `'openrouter'` — não há evidência de falha lá (Fase 92 já shipada e testada contra a API real). O set é fácil de estender se isso mudar no futuro.
- **Reaproveitamento de `_activeProvider`**: nenhum campo novo foi criado em `ChatSession` — o fix reaproveita `this._activeProvider`, já populado a partir de `LLM_PROVIDER` desde a Fase 63 (usado para `providerHasVision`).
- **Zero regressão para outros providers**: a chamada `llm.withStructuredOutput(planSchema)` sem segundo argumento permanece byte-idêntica para todos os providers exceto `lmstudio`, preservando o método `functionCalling` default que já funciona para OpenAI/Anthropic/Gemini/OpenRouter.
