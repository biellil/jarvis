executeAndAck flow (per D-12, D-13):
1. Lookup pendingAction pelo requestId
2. Chama window.jarvis.actions.executeAction({ action: pendingAction.action, path: pendingAction.path })
3. Se result.ok: sendAck(requestId, 'confirmed') — para viewContent: sendAck já não precisa do content pois o ACK WS é enviado pelo main via sendActionAck que lê do result.output
4. Se !result.ok: sendAck(requestId, 'denied')
5. setPendingAction(null)

NOTA sobre content flow: O `executeAction` IPC retorna `{ ok, content?, error? }` do handler.
O main (ipc/actions.ts) já tem o resultado. O ACK para o gateway (WS) é enviado separadamente via `sendAck` IPC que chama `sendActionAck(requestId, status)`.
Para incluir o content no ACK WS, o renderer precisa chamar sendAck com o content.
Verificar como sendAck no preload está definido (atualmente só aceita requestId + status).
Se necessário, estender sendAck no preload para aceitar content? opcional (ou usar channel separado).
Solução mais simples: o renderer passa content ao sendAck → preload passa para ipcMain.handle ACTION_ACK → main chama sendActionAck(requestId, status, content).

  const executeAndAck = useCallback(async (requestId: string) => {
    if (!pendingAction || pendingAction.requestId !== requestId) {
      console.warn('[useActionConfirmation] executeAndAck called with unknown requestId', requestId);
      return;
    }

    const result = await window.jarvis.actions?.executeAction({
      action: pendingAction.action as import('../../../shared/ipc-types.js').FileAction,
      path: pendingAction.path,
    });

    if (result?.ok) {
      // Pass content along for viewContent actions so ACK WS carries file content to gateway
      void window.jarvis.actions?.sendAck(requestId, 'confirmed', result.content);
    } else {
      void window.jarvis.actions?.sendAck(requestId, 'denied');
    }
    setPendingAction(null);
  }, [pendingAction]);

  return { pendingAction, sendAck, executeAndAck };
