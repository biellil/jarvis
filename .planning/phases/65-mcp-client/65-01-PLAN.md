<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| User filesystem → backend-ts process | `.env` / `.env.local` writes are OS-level — Phase 65 trusts the user editing these files. Watcher runs in same process; no cross-process trust crossing here. |
| backend-ts → external MCP server (HTTP) | Outbound HTTPS to a server URL the user explicitly configured. Bearer token transits this boundary. |
| Renderer → main process IPC | Renderer asks main to relay reload command. Phase 65 channels accept no user-supplied data (reload takes no args, get-status returns server-side state). |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-65-01 | Information Disclosure | `.env.example` accidentally committing a real bearer token | mitigate | Task 3 acceptance criteria explicitly grep for `Bearer .*[A-Za-z0-9]{20,}` and require all 3 vars to be empty after `=`. Per Pitfall 7 in RESEARCH.md. |
| T-65-02 | Elevation of Privilege | Trust mode (D-14): MCP tools execute without confirmation, including destructive ones (`send_email`, `create_invoice`) | accept | User explicitly opted in by configuring `.env`. Mitigation surface: `.env.example` warning block (Task 3) names D-14 + states user responsibility. Residual risk accepted per CONTEXT.md D-14. |
| T-65-03 | Denial of Service | Watcher fires on every `.env` save → reload thrashes connection | mitigate | Plan 03 will implement 250ms debounce + diff against MCP_SERVER_* keys (Pattern 3). Plan 01 only documents — actual mitigation in 65-03. |

Plan 01 mitigates T-65-01 directly via Task 3 acceptance criteria. T-65-02 is documented (acceptance) and consumed by Task 3's warning block. T-65-03 is referenced for Plan 03 to mitigate.
</threat_model>
