<setreply_risk_note>
**A9 from research:** `ChatInput.tsx` uses `setReply(result.data.message)` + `setTimeout(() => setState('idle'), 2000)` — this is a legacy UX pattern from Phase 12 that overlaps with `addAgentMessage`. Research recommendation is Opção B (remove setReply, trust SpeechBubble to be fed by ChatContext). BEFORE removing `setReply` from `handleStopRecording`, the executor MUST verify that `SpeechBubble` renders the agent message from `useChat().messages` and NOT from a prop `text` passed from ChatInput's local state.

**Read `apps/desktop/src/renderer/components/SpeechBubble/index.tsx` (or wherever SpeechBubble lives)** and check:
1. If it receives a `text` prop → `<SpeechBubble text={reply} />` in ChatInput creates a dependency. Keep `setReply` in PTT but strip the `setState` calls (use `sendAudioAndHandle` for state, `setReply` for bubble).
2. If it reads from `useChat()` → `setReply` is dead code. Remove.

The `text` prop currently appears in ChatInput.tsx line 218: `{reply && <SpeechBubble text={reply} />}`. Determine if that prop drives render or if SpeechBubble internally prefers `useChat().messages`.

**Decision policy:**
- If SpeechBubble takes a `text` prop that's actually used → KEEP the `setReply(result.data.message)` call BUT move it to a post-`sendAudioAndHandle` block. The state transitions are already handled by `sendAudioAndHandle`; setReply only needs the bubble text.
- If SpeechBubble reads from context → REMOVE `reply` state entirely from `handleStopRecording` (keep the `const [reply, setReply] = useState('')` for `handleSubmit` text flow which still uses it).

Record the decision in the SUMMARY.md.
</setreply_risk_note>
