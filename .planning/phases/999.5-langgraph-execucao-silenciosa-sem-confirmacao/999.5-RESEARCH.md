# Phase 999.5: LangGraph execução silenciosa sem confirmação obrigatória - Research

**Researched:** 2026-05-27
**Domain:** LangGraph agent interrupts, task approval memory, silent execution, conditional confirmations
**Confidence:** HIGH

## Summary

This phase removes mandatory interrupts from the LangGraph planner by introducing persistent approval memory, critical-action detection, and silent execution mode. The backend must implement a SQLite-backed approval cache keyed by plan step hashes, check it before interrupting, and route confirmation through chat (not blocking prompts). The Python client must suppress step-by-step progress output by default, displaying only final results.

The research confirms all decision patterns from CONTEXT.md are technically feasible within the existing TypeScript backend and Python client architectures. No breaking changes required; additions are purely additive to the current interrupt flow.

**Primary recommendation:** Implement in two backend waves: (1) approval memory + critical-check planner logic, (2) ChatSession awaitingConfirmation flag + silent event filtering in Python client.

## User Constraints (from CONTEXT.md)

### Locked Decisions

**D-01: Approval Memory Storage**
- SQLite table `approved_plans` with SHA-256 key (step descriptions normalized, lowercase, sorted)
- TTL: 90 days (configurable)
- Rationale: deterministic, no ML cost, integrates with Drizzle ORM, auditable

**D-02: Critical Actions Always Interrupt**
- Keywords: deletar|delete|remover|remove|apagar|erase|unlink|rm|trash|permission|chmod|chown|registry|system config|configuração do sistema
- Detection: scan `step.description` fields before approved_plans check
- Effect: bypass approval cache entirely for deletion/permission changes

**D-03: Planner Decision Flow**
1. Generate plan via `generatePlan()`
2. Check for critical keywords → if match, call `interrupt()` immediately
3. Check `approved_plans` with canonical key → if match within TTL, execute silently (no `interrupt()`)
4. No match → call `interrupt()` with `task:awaiting-confirmation`
5. On user confirmation → save entry to `approved_plans`, continue execution

**D-04: Confirmation via Chat (Keyword-First, LLM Fallback)**
- Keywords (zero latency): `s`, `sim`, `y`, `yes`, `n`, `nao`, `não`, `no`, `cancel`, `cancelar`
- LLM fallback: intent classification for non-keyword replies
- Implementation: `ChatSession.awaitingConfirmation` flag tracks `{ taskId, threadId }`
- When flag set: POST `/chat/stream` routes to `POST /tasks/:taskId/resume` instead of LLM completion
- JARVIS displays confirmation request as normal chat bubble, not blocking prompt

**D-05: Silent Mode in Python Client**
- New config field: `agentic_step_progress` (bool, default `False`)
- When `False`: events `task:step:start` and `task:step:end` received but NOT displayed
- When `True`: display per-step progress (current behavior)
- Always display: `task:error`, `task:cancelled`, `task:awaiting-failure-decision`
- Implementation: filter in `_handle_agentic_event()` before `_console().print()`

### Claude's Discretion

- **Approval key normalization:** Algorithm for step description hashing, whitespace handling
- **Critical keywords:** Exact list expansion beyond the minimum
- **ChatSession.awaitingConfirmation storage:** Field name, object structure, lifecycle
- **JARVIS confirmation message:** Exact wording when requesting approval
- **Config menu integration:** Where `agentic_step_progress` appears in `/config` menu

### Deferred Ideas (Out of Scope)

- ChromaDB semantic similarity for reformulated approvals (future, when corpus is large enough)
- Inline confirmation buttons in Electron GUI (splits code paths; defer for UI maturity)
- Progressive disclosure of steps in chat (defer for UI)

```typescript
// 1. Check for critical keywords
function hasCriticalAction(plan: Plan): boolean {
  const criticalKeywords = [
    'deletar', 'delete', 'remover', 'remove',
    'apagar', 'erase', 'unlink', 'rm', 'trash',
    'permission', 'chmod', 'chown', 'registry',
    'system config', 'configuração do sistema'
  ];
  return plan.steps.some(step => {
    const desc = step.description.toLowerCase();
    return criticalKeywords.some(kw => desc.includes(kw));
  });
}

// 2. Check approved_plans table
async function isApproved(plan: Plan, db: Database): Promise<boolean> {
  const key = canonicalPlanKey(plan); // hash of normalized steps
  const row = await db.query(
    'SELECT expires_at FROM approved_plans WHERE key = ? AND expires_at > datetime("now")',
    [key]
  );
  return row.length > 0;
}

// 3. Emit new event on auto-approval
writer?.({ kind: 'task:auto-approved', plan });

// 4. Modified planner node logic:

  const decision = interrupt({ kind: 'plan-confirmation', plan });
  // ... existing resume logic
} else if (await isApproved(plan, db)) {

} else {
  const decision = interrupt({ kind: 'plan-confirmation', plan });
  // ... existing resume logic
}
```

#### Pattern 2: Approval Key Generation (Canonical Hash)

**What:** Normalize plan step descriptions and generate SHA-256 hash for lookup

**Normalization rules:**
- Lowercase all text
- Trim whitespace from each step description
- Sort steps by `.id` (already ordered, but enforce)
- Concatenate normalized descriptions with `\n`
- Hash via `crypto.createHash('sha256')`

**Example:**
```typescript
function canonicalPlanKey(plan: Plan): string {
  const normalized = plan.steps
    .map(s => s.description.toLowerCase().trim())
    .sort()
    .join('\n');
  return crypto
    .createHash('sha256')
    .update(normalized)
    .digest('hex');
}
```

**Why this approach:**
- Identical plans (same steps, same order) always produce same key
- LLM reformulations of the same action produce different keys (acceptable; ChromaDB semantic version deferred)
- Deterministic — no ML required

#### Pattern 4: Approval Memory Persistence

**Schema (Drizzle table):**
```typescript
export const approvedPlans = sqliteTable('approved_plans', {
  id: integer('id').primaryKey({ autoIncrement: true }),
  key: text('key').notNull().unique(), // SHA-256 of normalized steps
```

**Lifecycle:**
1. User confirms plan via chat → `POST /tasks/:taskId/resume` receives `{ kind: 'confirm' }`
2. Executor saves to `approved_plans` after plan generation completes
3. TTL checked on lookup: `expiresAt > NOW()`
4. Expired entries can be pruned periodically or on startup

**Why this table:**
- Mirrors existing `actionsLog` pattern (Drizzle + SQLite)
- Plan JSON for audit trail (why was it approved?)
- Separate from `actionsLog` because `actionsLog` tracks PC actions, not LLM plans

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Hash-based deduplication | Custom binary format or trie | SHA-256 + SQLite lookup | Built-in, auditable, standard |
| Keyword detection | Regex with manual edge cases | Simple string containment (`.includes()`) | Phase requirements use exact keywords; simple substring match is sufficient |
| Config persistence | Custom JSON parser + file locking | Existing `save_config()` + Pydantic | Already proven thread-safe and atomic |
| Approval TTL | Manual timestamp arithmetic | SQLite `datetime()` expressions | DBMS handles edge cases (leap seconds, etc.) |
| Confirmation intent parsing | Full LLM call per reply | Keyword lookup + optional LLM fallback | Phase D-04 specifies keyword-first for zero latency |

**Key insight:** Approval memory is simple because it only needs content matching (same steps = same hash). Semantic similarity (reformulated steps) is explicitly deferred to ChromaDB phase. This keeps Phase 999.5 focused and proves the approval concept before scaling.

## Common Pitfalls

### Pitfall 1: Approval Cache Key Collision (Low Probability, But Possible)

**What goes wrong:** Two different plans hash to the same key, user approves one, second executes silently without approval

**Why it happens:** SHA-256 is cryptographically secure; collisions are negligible (~2^-128) for this use case

**How to avoid:** Keying strategy (D-03) normalizes steps, not full plan. If two unrelated plans happen to have identical step descriptions (rare), they should arguably be treated as equivalent

**Warning signs:** Repeated approvals for visually different plans; add audit log field `planJson` to `approved_plans` for review if needed

### Pitfall 2: TTL Expires During Execution

**What goes wrong:** Task is approved, executor starts running, TTL expires mid-execution, subsequent tasks reject the cache entry

**Why it happens:** Phase doesn't check expiry during execution, only at planner entry point

**How to avoid:** Current design is acceptable — approval is checked BEFORE execution starts. If execution takes > 90 days (not realistic for JARVIS), the next invocation of the same plan will re-request approval (safe degradation)

**Warning signs:** Logs showing "plan not found in cache" for plans user swears they approved recently → check `expiresAt` in SQLite

### Pitfall 3: Case Sensitivity in Keyword Detection

**What goes wrong:** User's plan step has `DELETE file.txt`, but keyword check looks for lowercase `deletar` only

**Why it happens:** Careless normalization

**How to avoid:** Pattern 2 normalizes step descriptions to `.toLowerCase()` before keyword scan. Always apply this in `hasCriticalAction()`

**Warning signs:** Plans with capital `DELETE` execute silently when they should interrupt → check keyword scan logic

### Pitfall 4: User Confirmation Lost if Backend Crashes

**What goes wrong:** User sends confirmation message, backend crashes before saving to `approved_plans`, next execution asks again

**Why it happens:** Approval save is queued, not blocking

**How to avoid:** This is acceptable degradation. Approval save is fire-and-forget (like embedding extraction); user won't notice if they re-confirm once. Alternative: make save blocking (rejected; blocks UX)

**Warning signs:** User complains about repeated confirmations; audit trail shows approvals missing from `approved_plans`

### Pitfall 5: Silent Event Mode Silences Errors (User Doesn't Know Task Failed)

**What goes wrong:** User sets `agentic_step_progress=False`, task fails, but `task:error` is displayed (per D-05). User sees error without context

**Why it happens:** D-05 specifies "always display errors" but also "suppress step events"; mismatch if task fails at step 2 of 5

**How to avoid:** `task:error` and `task:awaiting-failure-decision` are always displayed (Pattern 1 in Python). User gets error context. If they want full step context, they toggle `agentic_step_progress=True`

**Warning signs:** User sets silent mode, task fails, complains about lack of context → reassure they can toggle progress via `/config`

### Pitfall 6: Critical Action Detection Too Broad (All Deletion-Like Plans Interrupt)

**What goes wrong:** User approves a read-only plan that contains the word "remove" (e.g., "Remove highlighted text from display"), re-approval required every time

**Why it happens:** Keyword list too aggressive

**How to avoid:** Keyword list in D-02 is conservative: `delete`, `remove`, `trash` (file ops), `permission`, `chmod`, `registry` (system config). Context matters — D-02 specifies "ações críticas" (deletion/permissions), not all uses of keywords

**Warning signs:** False positives in logs; add plan JSON to audit trail for review

```typescript
const CRITICAL_KEYWORDS = [
  'deletar', 'delete', 'remover', 'remove',

  'permission', 'chmod', 'chown', 'registry',

  return plan.steps.some(step => {
    const desc = step.description.toLowerCase();
    return CRITICAL_KEYWORDS.some(kw => desc.includes(kw));
  });
}

export function canonicalPlanKey(plan: Plan): string {
  const normalized = plan.steps
    .map(s => s.description.toLowerCase().trim())
    .sort()
    .join('\n');
  return crypto
    .createHash('sha256')
    .update(normalized)
    .digest('hex');
}

export async function isApprovedPlan(
  planKey: string,
  db: /* Drizzle Database instance */
): Promise<boolean> {
  // SELECT * FROM approved_plans WHERE key = ? AND expires_at > NOW()
  const result = await db.query(
    `SELECT id FROM approved_plans WHERE key = ? AND datetime(expires_at) > datetime('now')`,
    [planKey]
  );
  return result.length > 0;
}

export async function saveApproval(
  planKey: string,
  plan: Plan,
  ttlDays: number = 90,
  db: /* Drizzle Database instance */
): Promise<void> {
  const now = new Date().toISOString();
  const expiresAt = new Date(Date.now() + ttlDays * 24 * 60 * 60 * 1000).toISOString();
  
  // INSERT OR REPLACE INTO approved_plans (key, plan_json, approved_at, expires_at, created_at)
  await db.insert(approvedPlans).values({
    key: planKey,
    planJson: JSON.stringify(plan),
    approvedAt: now,
    expiresAt,
    createdAt: now,
  }).onConflictDoUpdate({
    target: approvedPlans.key,
    set: { expiresAt },
  });
}
```

```typescript
      kind: 'plan-confirmation',
      plan,
    }) as ResumeCommand;
    
    if (decision.kind === 'confirm') {
      // D-03 step 5: Save approval on confirmation
      await saveApproval(planKey, plan, 90, db);
    }
    
    // ... handle decision (confirm/cancel/edit) ...
```

## Open Questions

1. **LLM Fallback for Confirmation (D-04 Deferred)**
   - What we know: D-04 specifies keyword-first parsing; LLM fallback mentioned but deferred
   - What's unclear: When/if to implement LLM intent classifier; adds latency; worth the complexity?
   - Recommendation: Keyword-only for Phase 999.5. Monitor user feedback; if too many invalid replies, add LLM fallback in 999.6

2. **Approval Expiry Messaging**
   - What we know: 90-day TTL; expired approvals silently fall back to interrupt
   - What's unclear: Should JARVIS tell user "This plan is new since last approval" on second execution?
   - Recommendation: Silent fallback acceptable. Add optional `task:plan-expired` event for logging if needed

3. **Semantic Expansion of Critical Keywords**
   - What we know: D-02 lists file deletion + permission keywords
   - What's unclear: Should network operations (delete API, shutdown) also be critical?
   - Recommendation: Stick to D-02 list for Phase 999.5. Network criticality is context-dependent; defer to future phase

4. **approval_plans Pruning**
   - What we know: 90-day TTL enforced at query time
   - What's unclear: Should there be a background job to DELETE expired rows?
   - Recommendation: Defer to maintenance phase. Query-time filtering is sufficient for MVP; table size negligible (<1MB for 1000s of approvals)
