Integrar o módulo `speaker` (Plan 01) e o toggle do menu (Plan 02) no pipeline de voz e LLM:

1. **voice_modes.py:** Em cada um dos 3 loops (`_ptt_loop`, `_wake_word_loop`, `_always_listening_loop`), entre `record_until_silence()` (ou equivalente) e `transcribe()`, chamar `_identify_speaker_safe(audio, config)` (helper interno que captura exceções e respeita `config.speaker_recognition_enabled`). Trocar `_queue.put(text)` por `_queue.put({"text": text, "speaker": speaker_result})` nos 3 lugares (SPK-07). Queue API é **dict** (não tuple) — decisão de revisão 2026-05-29 para extensibilidade.

2. **chat.py:** Atualizar `_await_input` para desempacotar item da Queue (dict {text, speaker} ou string legacy via guard); adicionar `_build_speaker_prefix(speaker_result, threshold)` helper que retorna `"[name]: "` (alta conf), `"[name?]: "` (baixa conf) ou `"[unknown]: "` (D-08); prefixar o `message` antes de chamar `_stream_response`; atualizar `_stream_response` para aceitar `speaker_result` e incluir header `x-jarvis-speaker: {name|unknown|''}` na requisição (D-11). System prompt fica no gateway — desktop-py injeta apenas no message body via prefixo + header (D-09).

3. **Compat reversa:** Se `speaker_recognition_enabled=False`, `_identify_speaker_safe` retorna `None`; Queue carrega `{"text": text, "speaker": None}`; `_build_speaker_prefix(None, ...)` retorna `""`; header `x-jarvis-speaker` NÃO é enviado. `_await_input` desempacota com guard que aceita string legacy (caso algum producer antigo) ou dict novo. Comportamento idêntico ao pre-Phase 89.

**Honra:** D-06 (timing — após captura, antes de transcribe), D-08 (hybrid injection prefix), D-09 (reconstruído a cada turno), D-10 (unknown não interrompe), D-11 (header sinaliza ChromaDB para skip de unknown).

**Nota sobre arquitetura:** O LLM e a memória ChromaDB rodam no **gateway** (Express/Node), não no desktop-py. A injeção D-08/D-09 ocorre no message body via prefixo (`[name]: `) que o LLM lê como contexto. O guard D-11 é sinalizado via header HTTP `x-jarvis-speaker` que o gateway pode consumir num phase futuro para implementar o skip-de-persistence (out of scope para Phase 89). Este plan estabelece o **contrato HTTP**.

Purpose: Sem esta integração, o speaker recognition é uma feature dormente — identifica mas nada acontece. Esta plan conecta tudo.

Output: ~50 linhas novas em voice_modes.py (helper + 3 sites de integração), ~60 linhas novas em chat.py (helper + alterações em _await_input/_stream_response/build_request_headers), 2 testes novos.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| voice thread → chat_loop main thread | Queue de dicts — race condition possível se item mutável compartilhado |
| desktop-py → gateway HTTP | Header x-jarvis-speaker carrega identidade do usuário |
| transcribed text + speaker name → URL query string | Message contém prefixo `[name]:` antes de URL-encode |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-89-03-01 | Tampering | Queue dict {text, speaker} (text, speaker_result) | mitigate | Pitfall 6 do RESEARCH — usar dict na Queue (não estado global mutável). Cada turno tem seu próprio item encapsulado. Garantido por `_queue.put({"text": text, "speaker": speaker_result})` sempre como par nomeado. Dict é decisão de revisão 2026-05-29 (extensível, vs tuple rejeitado). |
| T-89-03-02 | Information Disclosure | Header `x-jarvis-speaker` em request HTTP | accept | Speaker name vai para o gateway local (mesma máquina ou rede privada controlada pelo usuário). Não há transmissão pública. Risco aceito para feature local-only. |
| T-89-03-03 | Repudiation | ChromaDB persistence de unknown speaker | mitigate (parcial) | D-11: header `x-jarvis-speaker: unknown` sinaliza ao gateway para skip da gravação. Implementação completa do skip é gateway-side (out-of-scope Phase 89). Esta plan estabelece o **contrato HTTP** — gateway pode consumir o header em phase futuro. Documentar contrato em comentário no chat.py. |
| T-89-03-04 | DoS | identify_speaker exception derruba voice loop | mitigate | `_identify_speaker_safe` envolve a chamada em try/except — qualquer exceção retorna `None` e loga `[SPK] erro: {exc}`. Pipeline de voz continua. |
| T-89-03-05 | Spoofing | Speaker injection via texto transcrito malicioso | accept | Whisper pode transcrever um audio que contém `"[Maria]: hey"` literalmente. O prefixo `[name]:` aparece no message, e LLM pode ser enganado se confiar 100% no prefixo. Risco aceito — speaker recognition é assistive, não authoritative. Para enforcement real, gateway deve ler o **header** `x-jarvis-speaker`, não o body. |
