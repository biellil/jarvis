# Milestone v3.5: Emotional Voice Cloning TTS + Speaker Recognition

**Status:** ✅ SHIPPED 2026-06-02
**Phases:** 86-89
**Total Plans:** 11

## Overview

Substituição do Kokoro no Python Desktop por Chatterbox TTS com clonagem de voz por arquivo de referência, controle emocional via tags no texto, e implementação de speaker recognition via resemblyzer GE2E d-vector para identificação do falante com injection de contexto no LLM. Escopo: `apps/desktop-py` apenas.

## Phases

### Phase 86: Chatterbox Core

**Goal**: Chatterbox TTS disponível como provider em `tts.py`, instalável sem quebrar faster-whisper, com warmup na inicialização e fallback automático para Kokoro em qualquer erro
**Depends on**: Phase 85
**Requirements**: CHTB-01, CHTB-02, CHTB-03, CHTB-04
**Plans**: 4 plans

Plans:
- [x] 86-01-PLAN.md — Wave 0: Test infrastructure (fixtures + 15 testes RED para Chatterbox)
- [x] 86-02-PLAN.md — Wave 1: Packaging (pyproject.toml extra `chatterbox` + smoke install script) [CHTB-02]
- [x] 86-03-PLAN.md — Wave 1: Singletons + cascade de device + set_provider('chatterbox') [CHTB-01]
- [x] 86-04-PLAN.md — Wave 2: Warmup async + _chatterbox_speak + integração em init_tts/speak [CHTB-01, CHTB-03, CHTB-04]

**Key decisions:**
- torch do Chatterbox conflita com ctranslate2 do faster-whisper — usar `uv override-dependencies` + torch pinned (não `--no-deps`)
- torch-directml pinned com sys_platform == 'win32' marker
- Warmup async com Event signaling — init_tts retorna em <1s, speak espera até 15s
- Provider state degradation in-memory only — config persistido NUNCA muda em fallback

### Phase 87: Voice Cloning

**Goal**: JARVIS clona a voz de um arquivo de referência configurado pelo usuário, com validação de startup que impede falhas silenciosas
**Depends on**: Phase 86
**Requirements**: VCLONE-01, VCLONE-02, VCLONE-03
**Plans**: 2 plans

Plans:
- [x] 87-01-PLAN.md — Wave 1: Test scaffold (8 RED tests para VCLONE-01/02/03)
- [x] 87-02-PLAN.md — Wave 2: Implementation (config field + validation + voice cloning wiring)

**Key decisions:**
- `_validate_audio_prompt_path()` returns (bool, str) — caller prints message and sets state
- Empty path skips validation entirely
- `_generate_kwargs` dict pattern for conditional kwargs to generate()

### Phase 88: Emotion Tags + Config UX

**Goal**: Texto com emotion tags é processado corretamente — tags conhecidas ajustam parâmetros do modelo, tags desconhecidas removidas antes da inferência; menu `/config` expõe novas opções
**Depends on**: Phase 87
**Requirements**: EMOTE-01, EMOTE-02, CFGUI-01, CFGUI-02
**Plans**: 2 plans

Plans:
- [x] 88-01-PLAN.md — Emotion tag parser + _chatterbox_speak extension + config fields (EMOTE-01, EMOTE-02)
- [x] 88-02-PLAN.md — Config UX: chatterbox no menu + prompt inline + item Audio referência condicional (CFGUI-01, CFGUI-02)

**Key decisions:**
- `_EMOTION_TAG_MAP` uses (exaggeration, cfg_weight) tuple — lookup by tag_name, fallback to config defaults when tag=None
- Tag strip occurs ONLY in Chatterbox path — Kokoro/ElevenLabs/Murf receive original text
- All `[xxx]` patterns stripped from text_clean regardless of recognition — prevents literal tags being spoken
- Conditional menu item 8 checked per-iteration (not cached) — prevents stale display

### Phase 89: Speaker Recognition

**Goal**: JARVIS identifica quem está falando via resemblyzer GE2E d-vector, injeta nome no contexto do LLM com prefixo híbrido, e sinaliza ao gateway via header HTTP para guard ChromaDB
**Depends on**: Phase 88
**Requirements**: SPK-01, SPK-02, SPK-03, SPK-04, SPK-05, SPK-06, SPK-07, SPK-08, SPK-09, SPK-10
**Plans**: 3 plans

Plans:
- [x] 89-01-PLAN.md — Wave 1: speaker.py core (VoiceEncoder singleton, ProfileStore CRUD, identify_speaker, cosine helper) + RED to GREEN tests [SPK-01..06, SPK-10]
- [x] 89-02-PLAN.md — Wave 2: Enrollment UX no /config menu (toggle + submenu de perfis: adicionar/listar/remover) [SPK-09, SPK-10]
- [x] 89-03-PLAN.md — Wave 3: Pipeline integration (voice_modes Queue dict + chat.py hybrid injection + header x-jarvis-speaker para guard ChromaDB) [SPK-07, SPK-08]

**Key decisions:**
- resemblyzer GE2E 256-dim d-vector, ProfileStore em `~/.jarvis/speakers/*.npy`, threshold cosine ≥ 0.75
- Queue API migrada de tuple para dict {text, speaker} — extensível por design
- Prefixo de speaker aplicado em chat_loop (não em _stream_response) — desacopla responsabilidades
- `_identify_speaker_safe()` com try/except global — feature opt-in não deve quebrar pipeline
- `_safe_profile_name` mitigation contra path traversal (T-89-01-01)

## Milestone Summary

**Shipped:** 2026-06-02
**Phases:** 4 (86-89)
**Plans:** 11 total

**Key accomplishments:**
1. Chatterbox TTS integrado como 5º provider em `tts.py` com GPU auto-detect CUDA→CPU, warmup assíncrono e fallback automático para Kokoro
2. Zero-shot voice cloning por arquivo de referência .wav/.mp3 com validação de startup (duração ≥5s, extensão válida)
3. 8 emotion tags (`[angry]`, `[excited]`, `[emphasis]`, `[sad]`, `[embarrassed]`, `[soft]`, `[whispering]`, `[breathy]`) mapeadas para parâmetros Chatterbox; tags desconhecidas removidas silenciosamente
4. Menu `/config` expandido: seleção de provider chatterbox com prompt inline para audio reference path e item condicional "Audio referência"
5. Speaker recognition via resemblyzer GE2E — enrollment em 5 utterances, threshold cosine ≥ 0.75, hybrid injection `[Name]:` / `[Name?]:` / `[unknown]:` no contexto do LLM
6. Header HTTP `x-jarvis-speaker` propagado ao gateway para guard ChromaDB (skip de unknown_speaker em escritas)

**Known gaps (no audit — proceeded manually):**
- CHTB-01..04 foram checados como completos com base no ROADMAP (Phase 86 done) sem audit formal
- Testes de hardware manual (Chatterbox real, voice cloning end-to-end, speaker com hardware real) pendentes em HUMAN-UAT.md

**Tech debt:**
- Warmup timing: cold start de 5-10s ainda existe na primeira execução se chatterbox não estava pré-aquecido
- Speaker recognition threshold (0.75) é conservador por design — pode precisar ajuste por usuário
- `x-jarvis-speaker` header no gateway backend-ts não está sendo consumido ainda (contract HTTP definido, implementação futura)
