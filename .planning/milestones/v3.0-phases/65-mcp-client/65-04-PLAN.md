  <how-to-verify>
    **Prerequisites:**

    - You need access to one MCP server. Recommended options (pick whatever you have):
      a. **n8n cloud** — go to your workflow → MCP Server Trigger node → copy the production URL + bearer token from Header Auth credential
      b. **n8n self-hosted** — same flow on your local instance
      c. **Pipedream MCP** — https://mcp.pipedream.com/<token>/<app>
      d. **Any MCP server you control** that exposes at least 1 tool via Streamable HTTP or SSE
    - JARVIS dev environment running in another terminal (will start in Step 1).

    ---

    **Step 1 — Run the full Phase 65 backend test suite:**

    ```bash
    cd apps/backend-ts
    pnpm test src/mcp/client/__tests__ src/config/__tests__/env-watcher.test.ts src/session/chat-session.test.ts -- --run
    ```

    Expected: ALL tests green — manager + tool-adapter + env-diff + e2e-mock-server + env-watcher + chat-session (with the 2 new Phase 65 tests).

    **Step 2 — Verify silent boot (no MCP_SERVER_URL set, D-02):**

    1. Make sure `.env` has NO `MCP_SERVER_URL` (or it's commented out / empty)
    2. From repo root: `pnpm dev`
    3. Watch the backend boot logs. Expected ONE info line: `[mcp-client] disabled: MCP_SERVER_URL not configured`
    4. Open Settings → "Servidor MCP" nav item → "Cliente MCP" sub-block. Expected status: `Não conectado`
    5. JARVIS chat works normally (no errors, no missing tools — `recall_memory` + 11 native tools still active).

    **Step 3 — Configure .env with a real MCP server, restart, verify connect:**

    1. Stop `pnpm dev` (Ctrl+C)
    2. Edit `.env` (or create `.env.local`) and set the 3 vars from your MCP provider:
       ```
       MCP_SERVER_URL=https://your-n8n-instance.app.n8n.cloud/mcp/<workflow-id>
       MCP_SERVER_BEARER=<token>
       MCP_SERVER_NAME=n8n
       ```
    3. `pnpm dev` again
    4. Backend boot logs MUST contain (in order):
       - `[mcp-client] connected to n8n: N tools` (where N ≥ 1)
       - NO `[mcp-client] StreamableHTTP failed (...) trying SSE…` (or, if you see this, expected behavior — fallback worked, not a regression)
       - **CRITICAL**: there must be NO occurrence of the bearer token in any log output. Sanity check:
         ```bash
         pnpm dev 2>&1 | grep -i "Bearer\|<your-token-prefix>"
         # Should output nothing (Pitfall 7 mitigation)
         ```
    5. Settings UI → Cliente MCP sub-block: status updates to `Conectado a n8n: N tools`

    **Step 4 — Use an external tool in normal conversation (SC2):**

    1. Activate JARVIS via voice (PTT or wake word) or open the chat window
    2. Ask something that should trigger one of n8n's tools. Example for an n8n MCP server with a `send_email` tool:
       - "Manda um email pro João dizendo que o relatório está pronto" (PT-BR)
    3. Expected behavior:
       - JARVIS calls `n8n.send_email` (visible in `apps/backend-ts` console as a tool dispatch)
       - The actual email is sent (or whatever side effect the tool has — verify in n8n's execution log)
       - JARVIS narrates the result back in pt-BR: "Email enviado para o João" (or similar)
    4. Open SQLite tool_calls table or run:
       ```bash
       sqlite3 apps/backend-ts/data/jarvis.db "SELECT toolName, paramsJson FROM tool_calls ORDER BY id DESC LIMIT 5;"
       ```
       Expected: top entry has `toolName='n8n.send_email'` and `paramsJson` contains `_meta` field with `source=mcp-external` and `serverName=n8n` (D-15 audit)

    **Step 5 — Hot reload via .env edit (SC1 + D-09 + D-11):**

    1. With `pnpm dev` still running, open `.env` in your editor and change `MCP_SERVER_NAME=n8n` → `MCP_SERVER_NAME=automacao`
    2. Save the file (Ctrl+S in VS Code triggers atomic save — Pitfall 3 should absorb this)
    3. Within ~1s, backend logs:
       ```
       [env-watcher] MCP_SERVER_* changed (.env) — triggering reload
       [mcp-client] connected to automacao: N tools
       [mcp-client] reloaded after .env change — new tools active in next ChatSession (D-11)
       ```
    4. Settings UI → Cliente MCP sub-block: status label updates to `Conectado a automacao: N tools` (push subscription via onClientStatusChanged)
    5. **D-11 verification:** if a chat turn was IN PROGRESS during the .env edit (you can simulate by mid-streaming a long response), the active turn must finish using the OLD prefix (`n8n.*`). The NEXT turn picks up the new prefix (`automacao.*`).
    6. Send a new message asking for the same tool. Expected: tool dispatch shows `automacao.send_email` (new prefix), not `n8n.send_email`.

    **Step 6 — Graceful degradation when server dies (SC3 + D-16):**

    1. While JARVIS is connected to your n8n instance, simulate an outage:
       - **n8n cloud**: temporarily revoke the bearer credential in n8n
       - **n8n self-hosted**: `docker stop n8n` or kill the process
       - **Network simulation**: disconnect WiFi for ~10s after starting a tool call
    2. In JARVIS, ask for an n8n tool: "Manda um email…"
    3. Expected:
       - JARVIS does NOT crash. The chat session keeps responding.
       - The tool call returns a pt-BR error narrated via TTS — something like:
         "Não consegui acessar o n8n agora — tente novamente em alguns instantes" or similar (LLM narrates from the structured error string `MCP server n8n indisponível — tool send_email não pôde executar agora (...)`)
       - JARVIS's other (native) tools still work. Ask "que horas são?" or "lista os arquivos do desktop" — these run without issue.
    4. Backend logs: `[mcp-client]` warnings, NOT crashes.
    5. Restart your n8n. Click "Reconectar" in Settings → Cliente MCP sub-block.
    6. Status label updates back to `Conectado a n8n: N tools`. Next conversation turn can use n8n tools again.

    **Step 7 — Settings UI verification (D-10):**

    1. Settings → "Servidor MCP" nav item still shows the Phase 64 toggle (untouched).
    2. Below the toggle, "Cliente MCP" sub-block visible with:
       - Reconectar button (secondary variant, sm size)
       - Status label (right-aligned, gray text-fg-muted)
       - Helper text describing how to set MCP_SERVER_URL in `.env`
    3. Click Reconectar:
       - Button text changes to `Reconectando…` and is disabled during the call
       - On success: returns to "Reconectar" + status updates to `Conectado a {N}: {N} tools`
       - On failure: button returns to "Reconectar" + status shows `Erro: <message>`
    4. Status updates live without closing/reopening Settings (push subscription works).

    - [ ] Step 6: server outage produces pt-BR TTS error; native tools still work; reconnect via button works
