## Phase Details

### Phase 57: Google Gemini Provider
**Goal**: Users can select Google Gemini as their LLM provider in Settings and chat with it immediately
**Depends on**: Phase 56 (v2.2 complete)
**Requirements**: LLM-PROV-01
**Success Criteria** (what must be TRUE):
  1. User opens Settings, selects "Gemini" from the LLM provider dropdown, enters their GEMINI_API_KEY, and saves — no restart required
  2. JARVIS responds to a chat message using Gemini (verified by a model-specific reply or distinct latency)
  3. If GEMINI_API_KEY is absent or invalid, JARVIS degrades to LM Studio and shows an actionable error toast — it does not silently hang
  4. Gemini safety-filter null content produces a visible "JARVIS não pôde responder" toast rather than a blank or crash
**Plans**: 4 plans
Plans:
- [x] 57-01-PLAN.md — Backend types, config schema, and Gemini factory case
- [ ] 57-02-PLAN.md — ChatSession.swapLLM() and POST /internal/reload-llm endpoint
- [ ] 57-03-PLAN.md — Electron store API keys and RELOAD_LLM IPC handler
- [ ] 57-04-PLAN.md — Settings UI conditional API key inputs and tokenizer
**UI hint**: yes

### Phase 58: File Actions Refinement
**Goal**: Read-only file actions execute instantly without interrupting the user; destructive actions still require explicit confirmation; failed file opens fall back to the OS default app
**Depends on**: Phase 55 (LLM Actions — Tool Execution)
**Requirements**: FACT-10, FACT-11, FACT-12
**Success Criteria** (what must be TRUE):
  1. Asking JARVIS to "abrir pasta Downloads" or "mostrar conteúdo do arquivo X" executes immediately with no confirmation toast
  2. Asking JARVIS to "deletar arquivo X" or "mover Y para Z" still shows the confirmation toast and waits for the user before acting
  3. Opening a `.zip` file (or any file with no registered handler) falls back to the OS default app (xdg-open / start / open) without an error to the user
  4. A file path delivered via LLM is always canonicalized (path.resolve) before any open or fallback call — no symlink traversal possible
**Plans**: TBD

### Phase 59: System Controls
**Goal**: Users can control system volume and media playback with natural voice commands
**Depends on**: Phase 57 (any active LLM provider must be ready; no hard dependency on Gemini specifically, depends on Phase 56)
**Requirements**: SYSCTRL-01, SYSCTRL-02
**Success Criteria** (what must be TRUE):
  1. Saying "aumenta o volume" / "diminui o volume" / "muta o som" changes the OS system volume and JARVIS confirms verbally
  2. Saying "pause a música" / "próxima faixa" / "faixa anterior" sends the corresponding media key to the OS and the active media player responds
  3. On macOS, if Accessibility permission is missing, JARVIS shows the same actionable "Abrir System Settings" toast used for microphone in Phase 44 — media commands do not silently fail
  4. Volume and media tools are registered as LangGraph tools alongside existing PC tools — no new IPC channels required
**Plans**: TBD

### Phase 60: LM Studio Streaming Events
**Goal**: JARVIS uses the LM Studio Streaming Events protocol when the loaded model supports it, reducing first-token latency; falls back to standard SSE automatically when unsupported
**Depends on**: Phase 57
**Requirements**: LLM-PROV-02
**Success Criteria** (what must be TRUE):
  1. When LM Studio is the active provider and the loaded model supports Streaming Events, voice pipeline first-token latency is measurably lower than with standard SSE (verified by manual timing or soak log)
  2. When the loaded model does not support Streaming Events, JARVIS continues to respond normally via SSE fallback — no hang, no error
  3. A feature flag (e.g., USE_LM_STUDIO_STREAMING_EVENTS) in Settings controls the behaviour at runtime without requiring a restart
**Plans**: TBD

### Phase 61: Embedding Priority Queue
**Goal**: Memory embedding never blocks a chat request — embedding yields when a chat request arrives, and if it cannot be interrupted the chat request is served normally anyway
**Depends on**: Phase 60
**Requirements**: LLM-PRIO-01, LLM-PRIO-02
**Success Criteria** (what must be TRUE):
  1. Sending a chat message while a memory embedding is in-flight does not increase observed chat response time by more than 100ms compared to sending when no embedding is running
  2. If an in-flight embedding cannot be aborted (e.g., already past the abort checkpoint), the chat request proceeds to completion without error or timeout
  3. No AbortController leak is observable in a 30-minute soak run — heap growth remains within the Phase 56 QA-01 envelope (heap <100MB, RSS <200MB)
**Plans**: TBD
